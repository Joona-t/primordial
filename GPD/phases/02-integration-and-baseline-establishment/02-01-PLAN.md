  <action>
    After Task 1 resolves the runtime identity, characterize the target runtime's LLM compaction mechanism. This characterization determines the adapter strategy for Plan 02-02.

    Investigation steps:

    1. LOCATE the compaction codepath in the target runtime:
       - If OpenClaw: Find the compaction module (expected: context management / session handling). Read the source code or documentation for the compaction function. Identify: (a) what triggers compaction (token threshold?), (b) what the compaction function receives as input (full message history?), (c) what it produces as output (summary + truncated history?), (d) what side effects it has (session JSONL write? memory flush?).
       - If other runtime: Equivalent investigation using whatever documentation/source is available.

    2. CLASSIFY transparency level:
       - TRANSPARENT: Compaction function is callable/wrappable from Python. Pre-compaction state and post-compaction state are both programmatically accessible. Real-time callback exists.
       - SEMI-TRANSPARENT: Compaction writes evidence to a persistent store (JSONL, database, log). Pre/post state can be reconstructed from persistent records. No real-time callback.
       - OPAQUE: No evidence of compaction in any accessible store. Message history simply shrinks with no explanation.

    3. IDENTIFY hook points for forge integration (at least 2):
       For each candidate hook point, document:
       - Name and location (function, event, file path)
       - What it intercepts (pre-compaction messages, post-compaction summary, both)
       - Feasibility verdict: feasible / partially feasible / infeasible
       - Rationale for verdict

    4. ASSESS forge attachability:
       - Can forge `source_refs` be attached to compaction artifacts?
       - Do artifact IDs survive LLM compaction (identifierPolicy or equivalent)?
       - Can forge distinguish which artifacts were compacted vs retained?

    5. RECOMMEND adapter strategy:
       Based on transparency and hook points, recommend one of the three approaches from research:
       - Approach 1: Real-time adapter wrapping (preferred if transparent/semi-transparent with wrappable function)
       - Approach 2: Post-hoc JSONL transcript analysis (fallback if no wrappable function)
       - Approach 3: Prompt-layer interception (emergency fallback if compaction is opaque)

    6. ASSESS risk for Phase 4 provenance survival:
       - Under the recommended approach, what is the expected fate of `source_refs` after LLM compaction?
       - What is the risk that provenance chains break systematically? (This is the ROADMAP backtracking trigger.)

    Write results to docs/compaction-characterization.md with clear section headers for each investigation step.

    IMPORTANT: Qualify every use of "compaction" per convention #6. Use "LLM compaction" for context-window summarization and "forge trace compression" for lossless dedup. Unqualified "compaction" is FORBIDDEN.
